# 2. Strict linting and warning-free builds in CI

- **Status:** Accepted
- **Date:** 2026-08-29
- **Deciders:** Berend Klein Haneveld

## Context

The project had no automated checks: style drifted per commit, and compiler
warnings could accumulate unnoticed. Warnings in Swift are frequently the
early form of a real defect (unused results, deprecated API, unreachable code,
concurrency violations), and a warning list that is already long hides the new
warning that actually matters. Style discussions in review are a poor use of a
reviewer's attention when a linter can settle them.

## Decision

Every push and pull request runs a GitHub Actions pipeline with three jobs —
lint, build, and test — on the `macos-26` runner image:

- **Lint.** SwiftLint, installed fresh from Homebrew on every run so the latest
  release is always used, run with `--strict` so that a warning is an error.
  `.swiftlint.yml` carries the default rule set plus a set of opt-in rules, and
  deliberately contains no `disabled_rules` and no `excluded` paths.
- **Build.** `xcodebuild` for the tvOS simulator with
  `SWIFT_TREAT_WARNINGS_AS_ERRORS` and `GCC_TREAT_WARNINGS_AS_ERRORS` set to
  `YES`. The same settings are set in the Xcode project, so a local build fails
  on a warning exactly as CI does.
- **Test.** The unit and UI tests on a tvOS simulator, with the same
  warnings-as-errors settings applied to the test targets.

Exceptions to the linting rules — an inline `swiftlint:disable`, a disabled
rule, an excluded path — require explicit approval from the repository owner in
the pull request, and an ADR recording the reason.
`scripts/check-lint-exceptions.sh` runs first in the lint job and fails the
build when an exception appears without that process having been followed.

The commands live in `scripts/` rather than inline in the workflow, so that a
developer or an agent runs locally exactly what CI runs.

## Alternatives considered

- **Pinning a SwiftLint version.** More reproducible: a new SwiftLint release
  cannot turn a green branch red. Rejected because the owner asked for the
  latest linter at all times; the cost is an occasional failure caused by new
  rules, which is fixed by fixing the code.
- **Warnings as warnings.** Keeps the pipeline green while the code degrades.
  Rejected: the point of the pipeline is that the default branch stays clean.
- **Allowing inline `swiftlint:disable` freely.** Rejected: an exception that
  one person can add silently is not a rule. Requiring approval keeps the rule
  set honest and makes the cost of an exception visible.
- **A single CI job.** Rejected: separate jobs report which of lint, build or
  test failed at a glance, and run in parallel.

## Consequences

- Code that used to pass now has to be fixed rather than annotated; the type
  names generated by Xcode (`NPO_lightApp` and friends) were renamed to satisfy
  the `type_name` rule for this reason.
- CI can break without a code change, when SwiftLint releases a new rule. The
  fix is to comply with the rule, or to ask for an exception through the
  process above.
- The Xcode scheme is shared (`xcshareddata/xcschemes`), because CI needs to
  resolve `-scheme "NPO light"` from a fresh clone.
- macOS runner minutes are billed at a higher rate than Linux; the pipeline is
  kept to three jobs, with `concurrency` cancelling superseded runs.
